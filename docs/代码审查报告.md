## 一、严重（会污染工程 / 让安全机制失效）

### BUG-1 SCL 编码不一致 → **静默写入乱码块**（已复现 · 确凿）

**位置**：`TiaSession.cs:765 ReadSclText()` / `:812 ImportScl()`

预览用 `ReadSclText` 读文件（严格 UTF-8，失败回退 GBK），但真实导入时
`externalSource.CreateFromFile(name, path)` 把**原始文件**交给 TIA，而 **TIA 按 GBK/ANSI 读**。
两个解码器不一致。

**实测**：一个 UTF-8 编码、含中文变量名的 SCL：

```
=== 只导入 UTF-8 版 ===
{"ok":true,"result":{"created":[],"failed":["编码测试"],"details":[
  {"name":"编码测试","status":"failed","reason":"未在生成结果中找到该块"}]}}
```

看起来失败了。但**块其实已经建进工程**了：

```
=== 编译输出 ===
警告: 缂栫爜娴嬭瘯 (FB3) | When the input parameter '#鍚姩' is written, ...
块清单:  缂栫爜娴嬭瘯  [FB]  号3  SCL      ← 乱码块真的在工程里
```

**危害链**：
1. 返回 `failed` → 调用方以为没写进去
2. 实际写入了**名字乱码的块** → 工程被污染
3. 编译**不报错**（只有一条晦涩的形参/实参警告）→ 用户不会发现
4. 没有回滚 → 残留必须手工清理

同样的文件保存成 GBK 就完全正常，所以这是纯编码问题。

**修复方向**：导入前把文件转成 GBK 落到临时文件再交给 TIA；或检测到非 GBK 且含非 ASCII 时直接拒绝并给出明确指引。

### BUG-2 `ScanXmlBlockNames` 永远返回空 → **dry_run 安全预览形同虚设**（已复现）

**位置**：`TiaSession.cs:926`

```csharp
var nodes = doc.SelectNodes("//*[local-name()='Block']", ns);
```

但 SimaticML 的块元素是 `SW.Blocks.OB` / `SW.Blocks.FB` / `SW.Blocks.FC` /
`SW.Blocks.GlobalDB` / `SW.Blocks.InstanceDB`，**没有**叫 `Block` 的元素。

**实测**：

```
对一个真实有效的 XML 做 dry_run:
{"ok":true,"dryRun":true,"result":{"created":[],"skipped":[],"failed":[],"details":[]},"error":null}

该 XML 的根元素: <SW.Blocks.OB ID="0">
```

**危害**：
- `tia_import_lad_xml` 的 dry_run **永远报空** → 用户看不到"将会导入什么"，安全预览失去意义
- 真实导入后同样报空 → 无法确认导入了哪些块

**修复**：改用 `//*[local-name()='OB' or local-name()='FB' or local-name()='FC' or local-name()='GlobalDB' or local-name()='InstanceDB']`，或匹配 `starts-with(local-name(),'SW.Blocks.')`。

### BUG-3 `ImportLadXml` 强制覆盖，没有 overwrite 开关（读码确认）

**位置**：`TiaSession.cs:911`

```csharp
plc.BlockGroup.Blocks.Import(new FileInfo(xmlPath), ImportOptions.Override);
```

- 硬编码 `Override` → **总是覆盖同名块**，没有 `overwrite` 参数
- 对比 `tia_import_scl` 有 `overwrite` 参数且默认 false → 两个导入工具语义不一致
- 与宿主注释里承诺的安全规则 *"OB1 can only be appended to (never rewrite)"* **矛盾**
- dry_run 默认 true 只能保护"没显式关掉"的情况；一旦关了 dry_run，误传一个同名 XML 就会静默覆盖现有块

**修复**：加 `overwrite` 参数（默认 false），用 `ImportOptions.None` 并在已存在时跳过。

## 二、中等（功能错误 / 误导性结果）

### BUG-4 SCL 多块文件**误报失败**（已复现）

**位置**：`TiaSession.cs:786-796` 的正则表

```
@"FUNCTION_BLOCK\s+([A-Za-z_][A-Za-z0-9_]*)"
```

`END_FUNCTION_BLOCK` 里包含子串 `FUNCTION_BLOCK`，后面跟换行（`\s+` 匹配），
再捕获下一个标识符（因为 `_` 属于 `[A-Za-z0-9_]`），于是捕获出幽灵块名。

**实测**：含 2 个 `FUNCTION_BLOCK` 的文件

```
dry_run:   created: ["块A","块B","FUNCTION_BLOCK"]        ← 幽灵块
真实导入:  created: ["块A","块B"], failed: ["FUNCTION_BLOCK"]   ← 误报失败
```

**危害**：任何多块 SCL 文件导入后都会报一个假失败，掩盖真实的失败信息。

**修复**：正则加词边界/行首锚定，如 `(?<![\w])FUNCTION_BLOCK\s+`，并排除 `END_` 前缀。

### BUG-5 `ExportBlock` 的具体错误码被吞掉（已复现）

**位置**：`TiaSession.cs:1035-1051`

```csharp
try {
    if (File.Exists(targetPath))
        throw new TiaException("EXPORT_FILE_EXISTS", ...);   // ← 在 try 内抛
    found.Export(...);
}
catch (Exception ex) {                                        // ← 又把它抓回来
    if (ex.Message.IndexOf("Inconsistent") >= 0) throw new TiaException("EXPORT_INCONSISTENT_BLOCK", ...);
    throw new TiaException("EXPORT_FAILED", "导出块失败: " + ex.Message);   // ← 码被换成 EXPORT_FAILED
}
```

**实测**：

```
期望 code=EXPORT_FILE_EXISTS
实际 {"error":{"code":"EXPORT_FAILED","message":"导出块失败: 目标文件已存在，..."}}
```

**修复**：`catch (TiaException) { throw; }` 放在通用 catch 之前。

### BUG-6 宿主**没有并发控制**，但注释声称有（读码 + 实测）

**位置**：`mcp-server/Program.cs:25` 注释 vs 实际代码

```
注释: "This host holds the MCP connection and serializes every call"
实际: 全文没有 Semaphore / lock / Monitor / Mutex / Interlocked
```

每个工具调用各自 `proc.Start()` 起一个 worker 进程。两个 MCP 调用并发时，
会同时有两个 `TiaEngine.exe` attach 同一个 TIA 实例。

**实测**：3 个并发 `compile_plc` 都成功了 —— 但那是只读操作。
并发的**写操作**（导入块 / 建变量）风险更高，且 scope guard 是进程内的，不提供串行保护。

**修复**：宿主里加一个 `SemaphoreSlim(1,1)` 包住 `RunWorker`。

### BUG-7 `AssemblyResolve` 只搜一个目录，4 个必需程序集不在其中（已复现）

**位置**：`engine/Program.cs:19`（写死 `PublicAPI\V21\net48`）+ `:255 OnAssemblyResolve`

**实测**：每次运行 stderr 都有

```
[engine] resolve miss: Siemens.Engineering.Contract
[engine] resolve miss: Siemens.Engineering.ClientAdapter.Interfaces
[engine] resolve miss: Siemens.Engineering.ClientAdapter.MarshallerHook
[engine] resolve miss: Siemens.Engineering.ClientAdapter.MarshallerHook.Hmi
```

这些实际位于：

```
Siemens.Engineering.Contract                      -> Portal V21\Bin\PublicAPI
Siemens.Engineering.ClientAdapter.Interfaces      -> Portal V21\Bin\PublicAPI
Siemens.Engineering.ClientAdapter.MarshallerHook  -> Portal V21\Bin\PublicAPI\Client
```

现在能跑是因为 CLR 的默认探测**碰巧**找到了它们。但如果哪天探测失效，
这 4 行噪音会掩盖真正的解析失败。

**修复**：resolver 里多搜 `Bin\PublicAPI` 和 `Bin\PublicAPI\Client` 两个目录；
并统一 `TiaApiDir`（现在 csproj 的 HintPath 和 Program.cs 各硬编码一份）。

## 四、结论

**架构是站得住的**：net48 worker + .NET 8 宿主的分层是对的（Openness 确实不能跑在 .NET 8 里），
JSON 信封、stderr 分流、工程范围白名单、dry_run 默认开 —— 这些安全设计方向都对。

**有两个"看起来在保护你、实际没有"的问题**（BUG-1、BUG-2）：

- **BUG-1** 让 SCL 导入变成"报失败但实际写坏数据"—— **最危险**
- **BUG-2** 让 LAD 导入的 dry_run 预览永远为空 —— **安全网是假的**

配合 BUG-3（强制覆盖无开关），可以说**三个导入相关的安全机制都不可靠**。

**建议修复顺序**：
1. BUG-1 SCL 编码（数据污染）
2. BUG-2 块名扫描（安全预览失效）
3. BUG-3 LAD 覆盖开关（数据被覆盖）
4. BUG-4 SCL 幽灵块（误导性失败）
5. BUG-5 错误码（可诊断性）
6. BUG-6 并发控制（数据竞争）
7. BUG-7 程序集搜索路径（可维护性）
8. 8~22 按需
